# Spike 0001: why one b18 pass measured slower on the dispatch page (b18) on Edge (NVIDIA)

Date: 2026-11-26 (UTC). Machine: the owner's Linux laptop. Code: branch `spike-0001/pass-gap`, on top of
`spike-0001/wino-in-v2` (#77). All values below are quoted from the reports in this directory.

## The question

The dispatch page (#75, #76) measured one b18 pass at batch 16 at 29.0–32.6 ms. The check page's profile measured it at
25.0 ms (#71), and at 25.3–26.0 ms with the v2 input transform (#77). Both pages time it the same way:
`net.profile(batch, 'pass')`, awaited, after one warm-up call, with the same options in effect (GEMM v3, fused, f16,
scale8).

## What the clock logs showed

These logs come from the earlier runs, not this PR's: `nvidia-smi --query-gpu`, read-only, every 250 ms.

- **Dispatch page** (the #76 run, 2026-11-26T14:04 UTC): before each network timing, the page builds a plan, which
  compiles its shaders for about 3 s with the GPU idle.
  - In those gaps the SM clock fell to 315–600 MHz, the memory clock at times to 810 MHz, and the reason was `gpu_idle`.
  - The timed passes then ran as the clock climbed: 315, 570 and then 1365 MHz across 08:04:11.3–11.8 (local time).
- **Check page:** profiling comes straight after about 1.5 s of benchmarking the same plan. Across its fused variant's
  benchmark and profile (the #77 run, 08:24:54.2–56.7 local time), the SM clock was 1365–1725 MHz, and 1455–1725 MHz from
  08:24:54.4 on.

## The test

The dispatch page now keeps the GPU busy with the same pass for `networkWarmUpMs` (default 1000) after building each
plan, before timing it. `?networkWarmUpMs=0` restores the old behaviour. Four runs, alternating, one after another, each
in a fresh instance of the separate Edge (the launch used in #48, no flags added). Adapter
`{"vendor":"nvidia","architecture":"ampere","device":"","description":""}` in every report, all `ok: true`. Each run's
clock log is beside its report.

**`gpuPassMs`** (median of 7; in brackets, the warm-up passes):

| Run | `networkWarmUpMs` | Batch 16, plan 16 | Batch 16, plan 64 | Batch 32, plan 32 | Batch 32, plan 64 | Batch 64, plan 64 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 0 | 44.433 | 28.967 | 48.89 | 47.841 | 87.556 |
| 2 | 1000 | 25.362 (24) | 24.642 (27) | 46.072 (16) | 45.613 (15) | 86.835 (9) |
| 3 | 0 | 29.295 | 26.149 | 48.89 | 50.332 | 85.721 |
| 4 | 1000 | 23.855 (23) | 23.855 (27) | 44.368 (16) | 44.368 (17) | 84.017 (9) |

With the warm-up, batch 16 measured 23.855–25.362 ms. That's within or below the check page's 25.3–26.0 ms. Without it,
batch 16 measured 26.149–44.433 ms.

## Conclusion

On this evidence, the dispatch page's slower passes were measured while the GPU was coming out of idle. The engine
didn't lose that time. I haven't measured whether the search pages ever wait long enough for the GPU to idle and lower its
clocks.
