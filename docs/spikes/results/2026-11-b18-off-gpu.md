# Spike 0001: Phase 4, part 1, the review's time off the GPU (b18) on Edge (NVIDIA): closed

Date: 2026-11-26 (UTC). Machine: the owner's Linux laptop (RTX 3080 Laptop GPU, Intel Core i9-11900H). Browser: the
separate test Edge, with `--enable-unsafe-webgpu` for the "with the flag" runs (matrix hardware, as in #87) and without
it for the others. Code: branch `spike-0001/off-gpu`, on top of `spike-0001/browser-flags` (#88). Every figure below is
quoted from, or computed from, the reports in this directory.

## Outcome

**Closed by its stop rule, with an improvement kept.** The goal was a review whose wall time is at most 1.06 × its GPU
busy time, at batch 16 two at once (the review's default), with and without the flag. It was to close if the ratio
stayed above 1.10 after fixing what the measurement showed.

- **The cause, measured:** the GPU waits for the searches' own JavaScript, at the start of each turn. In steady state
  the two searches alternate and the GPU idles about 0.1 ms between passes. When a search finishes a turn, its last
  calls are small and the next turn's root evaluation has one position. Their passes take 4–9 ms, shorter than the
  other search's next step of JavaScript (about 7–10 ms), so the GPU idles about 10–12 ms once per turn.
- **The fix:** three changes that make the search's JavaScript faster and leave its results unchanged. On a
  repeatable benchmark the search's JavaScript took 34–35% less time.
- **Without the flag:** wall ÷ GPU-busy went from 1.101–1.107 to 1.073–1.080, and the GPU's idle time fell by
  18–31%. That's below the stop threshold but above the goal.
- **With the flag:** 1.113–1.154 before, 1.134–1.158 after. No change is resolved, and the ratio is still above 1.10.
- **Results unchanged:** in every pair of runs the review made the same number of evaluations and agreed with native
  KataGo's best move on the same turns.

**Change from prior, and against native.** Batch 16, two at once. Each pair was run in alternation (old, new) in fresh
test browsers. Native's `totalMs` is 16412.1–16596.1 (#80).

## How it was measured

- **A breakdown of the GPU's idle time**, in the search benchmark's review trace (`test/gpu/check.js`, `offGpu`). The
  shared evaluator records when each search request was queued, sent and answered, and which search made it
  (`reviewGame`'s `trace` option, measurement only). The network's trace records each call's times and GPU
  timestamps. The GPU timestamps are placed on the page's clock at the earliest offset consistent with every call; the
  range of consistent offsets was 0.7–1.4 ms wide in every kept run. Idle time is split two ways:
  - **by state:** what was happening while the GPU sat idle;
  - **by path:** each gap is put down to the path of the call that ends it, from the previous answer to the same
    search through its JavaScript, queueing, encoding and submission.
- **The raw timeline** (`?traceRaw=1`): every call and request of a review.
- **CPU profiles** of the page over the Chrome DevTools Protocol, and of a Node run of the searches. They're used only
  to rank costs, since the profiler slows the code it measures.
- **A repeatable benchmark of the search's JavaScript** (`scripts/search-cpu-bench.mjs`, new). The review's turns run
  in Node, one at a time at batch 16, with a stand-in network whose outputs are a fixed function of its inputs, so a
  build that gives the same results grows the same trees. It reports the searches' time outside the network
  (`Search.stats.cpuMs`), as the median of 5 runs. Whole browser runs can't measure these changes: in the same code,
  the search's JavaScript per request varied by half between runs, with the CPU's clock.
- **The A/B:** before and after, with and without the flag, two runs each, alternated, each in a fresh test browser.
  CPU clocks were logged every 250 ms (`…-cpufreq.csv`: time, mean of all cores in MHz, busiest core in MHz).
- **Reports** (`2026-11-b18-off-gpu-…`):

  | Report | Time (UTC) | What |
  | --- | --- | --- |
  | `breakdown` | 20:11:26 | the breakdown, on the code before this part, with the flag |
  | `timeline` | 20:45:20 | the raw timeline of the batch-16, two-at-once mode, on the code after this part, with the flag |
  | `base-auto-1`, `new-auto-1`, `base-off-1`, `new-off-1`, `new-auto-2`, `base-auto-2`, `new-off-2`, `base-off-2` | 20:56:50–21:13:46 | the A/B, in that order |
  | `cpu-bench.jsonl` | after the A/B | the repeatable benchmark, before and after, alternated |

  Each browser run has its GPU clock log (`…-clocks.csv`) and, for the A/B, its CPU clock log.
- **Not kept:** about a dozen development runs of the review while the breakdown and the fixes were built, and the CPU
  profiles (1.7 MB each). Their figures quoted below are marked as development runs.

## What the measurement showed

**The breakdown** (`breakdown`, batch 16 two at once, with the flag, before this part): the review took 27032.9 ms,
with the GPU busy for 23652.3 ms and idle for 3381 ms.

| Split | Largest part | Other parts (ms) |
| --- | --- | --- |
| By state | `mapWait` 2597.4 ms: a pass had ended and its outputs weren't readable yet | submitted 427.3, encoding 281.4, search 41.1, queued 30.2 |
| By path | `search` 2627.5 ms: the next call's search was running its JavaScript | submitted 427.3, encoding 283.8, queued 30.2, mapWait 6 |

The two splits agree once the timeline is read:

- **What the gaps are:** the outputs that weren't readable belong to the call that has just finished. The gap ends
  when the *other* search, which was still running its JavaScript, sends its next call.
- **Why outputs waited:** a pass's outputs took a median of 2.2 ms to become readable, but 9.9 ms at the 90th
  percentile. The browser can only deliver them when the page's one JavaScript thread is free.

**The timeline** (`timeline`, after this part, with the flag; ms from the first call):

| Call | Search | Batch | Request queued | Pass | GPU idle before it |
| ---: | ---: | ---: | ---: | --- | ---: |
| 406 | 1 | 5 | 6959.7 | 6973.7–6983.0 | 0.1 |
| 407 | 0 | 16 | 6983.8 | 6985.3–7004.1 | 2.3 |
| 408 | 1 | 1 (next turn's root) | 6985.2 | 7004.2–7008.4 | 0.0 |
| 409 | 0 | 16 | 7016.3 | 7019.1–7037.6 | 10.6 |

- **What happens at a turn's start:** search 1 ended its turn with 5 positions, then evaluated its next turn's root
  alone. Search 0 had its outputs from call 407 at 7006.7 and queued its next request at 7016.3, after 9.6 ms of its
  own JavaScript.
- **How often:** the same pattern recurs before calls 414, 421 and 428, with gaps of 11.8, 12.0 and 11.8 ms. Between
  turns the gaps are 0.1 ms.
- **The root's outputs:** call 408's outputs became readable 9.5 ms after its pass. The thread was busy with search
  0's JavaScript until 7016.3.

KataGo has the same pattern, a root evaluation before each turn's search, but its search threads run in parallel on the
CPU. In the browser they share one thread, so the search's JavaScript time is what sets these gaps.

**Where the search's JavaScript went** (CPU profile of the page over a whole search benchmark, before this part;
inclusive times, slowed by the profiler): the searches took 31.1 s.

## What each fix did

Repeatable benchmark, median of 5 runs (ms). The rows come from two development sessions, and the machine's speed
differed between them: the "before" figure was 9194.1 in the first and 8151.7–8192.1 in the A/B. Changes are within a
session.

| Fix | Before | After | Change | Kept |
| --- | ---: | ---: | ---: | --- |
| 1. Reuse ladder results across boards | 9194.1 | 6272.9 | −31.8% | yes |
| 2. Copy a board without building an empty one first | 6272.9 | 6136.2 | −2.2% | yes |
| 3. Superko bans without copying the board | 6104.2 | 5815.6 | −4.7% | yes |
| Superko bans prefiltered by a Zobrist hash, computed per move | 5474.8 | 6502 | +18.8% | no |
| The same, with the hash kept up to date by the board | 5608.4, 5618.4 | 6381.5, 6353.6 | +13% to +14% | no |

1. **Ladders (`encodeHistoryV7`'s new `ladders` option):**
   - **What KataGo does:** it searches ladders on three boards for every input: the current one and the two before
     it.
   - **The fix:** in a search, the two earlier boards are the node's parent's and grandparent's, already searched
     when those nodes were encoded. Each search now keeps the ladder results by board (its colours and ko point, which
     are all the ladder search reads), and replays them.
   - **Check:** the inputs are identical with and without the cache, in any order, over the 14 golden positions and
     every turn of the review game (`test/ladder-cache.test.mjs`).
2. **Board copies:** a copy used to build an empty board, then overwrite it. It now copies the arrays directly.
3. **Superko bans:**
   - **Before:** after every move, the history copied the board and played each candidate point to build the
     position's key.
   - **After:** it builds the key after the move directly: the new stone, minus the stones it captures (or, for a
     suicide, minus its own chain). This is what KataGo's `getPosHashAfterMove` does.
   - **Check:** the bans equal a brute-force check (each move played on a copy and looked up among the earlier
     positions) at every move of 72 random games on 4×4 to 6×6 boards. The games use Tromp-Taylor, AGA, Chinese and
     New Zealand rules, with captures, suicide and repeated positions (`test/superko.test.mjs`).
4. **Not kept:** a Zobrist hash prefilter for the superko keys, KataGo's own approach, in two forms. Both measured
   slower:
   - hashing the whole board after every move;
   - updating the board's hash on every stone placed and removed, which the ladder search does thousands of times.

## What remains

- **The ladder search on the current board:** 25% of the search's JavaScript in a Node profile after the fixes.
  - **The likely cause:** each move the ladder search plays snapshots five whole board arrays to undo it, where
    KataGo records only what the move changed.
  - **The fix it points to:** porting KataGo's incremental undo, which is a rewrite of the board's undo.
- **The pass-alive area:** 17%.
- **Postprocessing and symmetry:** 14%.
- **Turn starts:** the gaps there come from the review running two searches on one thread. With four at once, wall ÷
  GPU-busy was 1.021–1.055 in every A/B run, before and after.
