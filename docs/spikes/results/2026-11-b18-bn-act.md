# Spike 0001: Phase 4, part 3, batch norm (b18): kernel goal met, review change too small to measure

Date: 2026-11-26 (UTC). Machine: the owner's Linux laptop (RTX 3080 Laptop GPU). Browser: the separate test Edge,
with and without `--enable-unsafe-webgpu` (the flag). Native: KataGo v1.18.2, CUDA, `analysis_example.cfg` as it is.
Every figure below is quoted from, or computed from, the reports in this directory (prefix `2026-11-b18-bn-act-`).

## Outcome

The goal was for batch norm, timed on its own in the network, to reach at least 80% of copy bandwidth. The stop rule
was below 70% after fixes.

- **Kernel goal met at the median.** Batch norm v3 (8 values per thread, now the default) is at 78.4–85.1% of copy
  bandwidth at batch 16, median 83.7%, over 10 runs. That's against 55.1–56.1% for v1 (one value per thread) in 4 runs.
  At batch 64 it's at 93.3–95.1%, against 57.2–58.1%.
- **2 of the 10 batch-16 runs were below 80%** (78.4% and 79.2%, both without the flag). The batch-16 times fall into two
  groups, about 0.87–0.91 ms and 0.94–0.95 ms.
  - **Within a run:** the repeats usually stayed in one group. In three runs (v2c, v3c, v3d) they spanned both.
  - **v2** (4 values per thread) showed the same two groups.
  - **Ruled out:** the copy ceilings measured in the runs stayed at 347.5–351.1 GB/s. The GPU clock logs of the
    alternated runs showed no difference between the groups.
  - **The cause isn't known.**
- **The review's change is too small to measure.**
  - **Without the flag:** the review took +0.5% longer with v3 than with v1, within the spread between the two v1 runs
    (1.2%).
  - **With the flag:** it took 7.9% less time. That's more than batch norm can explain: its whole cost in the network is
    about 1 ms of the 17.5 ms batch-16 pass. In the same runs the GPU's busy time varied by up to 10.5% between runs
    of the same build. The v3 runs also had faster CPU clocks.
  - **The expected change (an assumption, not measured):** about 0.3 ms less per batch-16 pass in the network
    (below). At the review's mean batch of about 12, that's about 1% of its GPU time.
- **Results:** identical with v1 and v3. Every variant passes the goldens check, 38 with the flag and 33 without,
  including identical results across call sizes and concurrent calls. The review's evaluation counts and agreement
  with native are the same with v1 and v3.

## What changed

- **`BN_ACT_V2`** (`src/gpu/kernels.ts`): batch norm, activation and mask, the same function as `BN_ACT`, with `per` (4
  or 8) consecutive values per thread.
  - It loads and stores 4 values at a time.
  - It finds each thread's board, channel and point with one division, then steps from there.
  - It needs the layer's channels to be a multiple of `per`. That makes channels × area a multiple of `per`, as the
    area (361) is odd.
- **`GpuNetwork` option `bnAct`:** `'v1'` (`BN_ACT`), `'v2'` (4 per thread) or `'v3'` (8 per thread, the default).
  Layers whose channels aren't a multiple of 4 or 8 use v1. All of b18's batch norms have 48, 64, 128, 192 or 384
  channels, so they all use v3.
- **The check page** checks v1, v2 and v3, fused and unfused, in f32 and f16, and v2 with matrix hardware.
- **No difference from KataGo's function.** KataGo's CUDA backend fuses batch norm differently, but this is the same
  function the engine already computed, done with fewer threads.

**Against part 1's "after" runs** (1.45–1.57 with the flag, 1.90–1.97 without, same build as v1 here): the ranges
overlap.

- **With the flag, the GPU's busy time varied between runs of the same build in every mode,** by more than batch norm's
  whole cost:
  - batch 16 one at a time: 18029.2 and 17519.3 ms with v1, 17429.4 and 15768.3 ms with v3;
  - batch 64: 23035.9 and 22195.7 ms with v1.
- **The evaluation counts and agreement with native** were the same for v1 and v3 in every mode except one.
  - **The exception:** batch 16 four at once, in the first v1 run with the flag, made 20559 evaluations, where every
    other run made 20754.
  - **What that suggests (not checked):** with four searches at once, the network's batches can form differently from
    run to run.
  - **Scope:** it's not the review's default mode, and it was not looked into in this part.

## What's left of the gap

At 1.40–1.59 with the flag and 1.87–1.92 without in these runs, the gap is still mostly network throughput on the GPU
(part 2's table). Batch norm was the last Phase 4 item on it. This closes Phase 4.
